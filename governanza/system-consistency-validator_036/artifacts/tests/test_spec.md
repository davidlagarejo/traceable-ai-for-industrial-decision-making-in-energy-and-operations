# Test Spec — System Consistency Validator

Motor ID: motor_036

## happy_path

- a bounded screening package with aligned claim summaries, visible sections, scenario evidence and TAD surfaces passes with `can_render_pdf=true`;
- a bounded structural-primary package that satisfies the thesis-driven body contract also passes;
- a bounded congruence-enabled package passes when peer framing, measurement logic, finance/physics dependency and local-binding posture remain coherent.

## sparse_case

- minimal but internally coherent packages should still pass when they remain within bounded evidence posture;
- packages with missing but explicitly inadmissible body content should fail only where the contract requires it, not because the validator invents extra requirements.

## malformed_input

- incomplete output-mode classifiers, missing claim traces or mismatched chapter inventory must fail;
- promoted declared input, unresolved entity conflicts or foreign chart case context must fail;
- visible sections that contradict authoritative screening or structural state must fail.

## edge_cases

- invalid comparison risk cannot be smuggled in as observed peer evidence;
- hardware recommendations must follow cheapest-valid-source logic;
- permit or regulatory signals cannot become operational proof;
- finance claims must preserve physical dependency;
- expanded structural TAD actions must obey structural claim permissions.

## pass_criteria

- the validator emits a complete check matrix;
- the critical failure subset is correctly projected;
- binary render gating remains correct;
- the direct validator suites pass.

## fail_criteria

- `can_render_pdf` is true while any critical inconsistency remains;
- blocking reasons cannot be traced back to stable `check_id`s;
- visible report surfaces outrun authoritative governance surfaces.
