# Strategic Regression Audit — Conditional Archetypal Intelligence

Produced at: 2026-05-07

## Purpose

This audit answers one question:

Why did the framework improve in epistemic control while regressing in strategic intelligence?

The answer is not:

- "the system became safer"
- "the system needs softer governance"
- "the system should speculate more"

The answer is:

the framework is increasingly good at blocking false closure, but it now collapses too much of the structural reasoning lane into `inadmissible_thesis`, and that collapse suppresses client-useful conditional intelligence that should remain admissible.

That is a strategic regression.

---

## Executive Verdict

The regression is real.

The framework did **not** lose the underlying structural-intelligence architecture. The architecture is still present in:

- `motor_016` section contract, including `Conditional Opportunities` and a thesis-driven structural hierarchy;
- `motor_051`, which still builds fair-comparison logic, invalid-problem-frame logic, and cross-layer congruence;
- `motor_054`, which still builds gold nuggets, congruence-side TAD, latent combinations, and strategic framing;
- the skill lane, which still produces bounded warehouse/manufacturing/building combinations with admissible `allowed_language`.

The regression happened because the final synthesis lane now applies a stronger-than-intended hard gate:

1. unresolved asset identity or route-state uncertainty can force `target_not_yet_structurally_modelable`;
2. that state propagates into `inadmissible_thesis`;
3. `inadmissible_thesis` then empties contradiction, redesign, fair-comparison, loss-pattern, finance-to-physics, and gold-nugget surfaces at the executive-thesis layer;
4. `report_compression` then performs a near-total `inadmissible_bypass`, removing the client-facing structural body instead of preserving a conditional-intelligence layer.

So the framework is no longer only blocking false certainty.

It is increasingly blocking conditional strategic thinking.

That is the wrong direction.

---

## Central Rule

`Asset identity uncertainty blocks local claims, but MUST NOT block conditional archetypal intelligence.`

### Why this rule is critical

Because ZLab is not a claim-denial framework.

ZLab exists to build a congruence brain that can:

- detect wrong problem framing;
- identify invalid comparisons;
- surface dominant variables;
- warn when the benchmark is wrong;
- warn when the denominator is wrong;
- warn when the value-capture boundary is wrong;
- surface recurring industrial loss patterns;
- block premature CAPEX while still moving the client's thinking forward.

If identity uncertainty blocks all of that, the framework preserves safety at the cost of usefulness.

### Problems this rule resolves

1. It separates `closure` from `thinking`.
2. It prevents `not yet locally bounded` from degenerating into `nothing strategic can be said`.
3. It preserves fair-comparison intelligence even when peer comparison is not yet admissible.
4. It preserves pattern intelligence even when local diagnosis is prohibited.
5. It preserves executive value without permitting fabricated local truth.

### Errors this rule avoids

1. false local diagnosis
2. fake ROI or savings logic
3. peer superiority claims
4. benchmark superiority claims
5. compliance closure
6. definitive retrofit recommendations

### Outputs this rule permits

1. conditional archetypal hypotheses
2. bounded structural contradictions
3. wrong-denominator warnings
4. wrong-variable warnings
5. fair-comparison requirements
6. finance-to-physics dependency warnings
7. measurement-minimality guidance
8. gold nuggets bounded as strategic reframes rather than local facts

### Outputs this rule still prohibits

1. "this asset has charging losses"
2. "this building is inefficient because X"
3. "peer assets outperform this asset"
4. "this retrofit will save Y"
5. "this site should deploy a digital twin"
6. "this case is bankable"

## 2. Causa Raíz

### Qué cambió en la lógica

Antes, el sistema podía producir algo como:

`this may be a charging / dock-loss / control-boundary / tariff-exposure problem`

sin afirmar que ya sabía la verdad local.

Ahora, una parte del stack hace este colapso:

1. si el target no queda suficientemente clasificado como `OPERATING_ASSET`, `research_router.py` fija `route_state` a `target_not_yet_operationally_bounded`;
2. muchos motores de congruencia usan `if route_state != operational_asset_candidate: return []`;
3. si `selected_archetype_id == target_not_yet_structurally_modelable`, `system_abstraction.py` llena todo el abstraction object con un unresolved statement `INADMISSIBLE_CLAIM`;
4. `executive_thesis.py` exige `problem_frame_active && dominant_contradiction`;
5. si falla eso, devuelve un thesis vacío con `evidence_state = INADMISSIBLE_CLAIM` y `thesis_state = inadmissible_thesis`;
6. `report_compression.py` convierte eso en `inadmissible_bypass`, dejando `sections = []`.

### Qué motor domina incorrectamente

El dominador incorrecto no es un motor de inteligencia, sino la combinación de:

1. `route_state` hard gate
2. `selected_archetype == target_not_yet_structurally_modelable`
3. `problem_frame_active` como interruptor maestro del thesis
4. `inadmissible_thesis -> inadmissible_bypass`

### Qué validación está sobrebloqueando

La validación correcta sería:

- bloquear `local truth closure`
- bloquear `definitive diagnosis`
- bloquear `financial closure`

La validación actual además bloquea:

- contradiction synthesis
- fair-comparison warnings
- loss-pattern framing
- finance-to-physics warnings
- gold nuggets
- conditional redesign posture

Ese segundo bloque es el error.

### Qué regla está colapsando hipótesis

La regla equivocada de facto es:

`If the asset is not sufficiently bounded, structural reasoning itself becomes inadmissible.`

La regla correcta debe ser:

`If the asset is not sufficiently bounded, local claims become inadmissible, but structural hypotheses remain admissible when explicitly labeled as archetypal, conditional, falsable, and non-local.`

### Qué outputs fueron degradados innecesariamente

1. `dominant_contradiction`
2. `invalid_comparison_risk`
3. `dominant_loss_logic`
4. `finance_to_physics_take`
5. `maintenance_reality_take`
6. `top_gold_nuggets`
7. `what_is_admissible_now`
8. `top_actions`
9. `conditional_redesign`
10. `interpretive_signal_register`

## 3. Balance Correcto

### A. Local Truth Claim

Ejemplo:

`This warehouse has charging-related demand losses.`

Esto sigue prohibido sin evidencia local suficiente.

Por qué:

1. afirma un estado local como hecho;
2. presupone que el patrón ya fue observado;
3. puede inducir CAPEX o underwriting falso.

### B. Structural / Archetypal Hypothesis

Ejemplo:

`If this asset behaves like a logistics node with electric MHE and demand-sensitive tariff exposure, charging-related demand overlap becomes a structurally plausible hypothesis that deserves falsification before any owner-capturable efficiency claim.`

Esto debe seguir permitido.

Por qué no es alucinación:

1. no afirma hecho local;
2. explicita el arquetipo;
3. explicita la condición;
4. explicita la evidencia mínima;
5. explicita cómo se falsaría;
6. no cierra ni ROI ni diagnóstico.

### Por qué bloquear el segundo destruye valor

Porque sin ese nivel de razonamiento el framework sólo puede decir:

- falta dato
- falta horario
- falta GFA
- no modelable

Eso protege, pero no piensa.

El usuario necesita que el framework ya pueda decir:

- quizá el benchmark es inválido;
- quizá el problema es el denominador;
- quizá el driver es dock activity;
- quizá el costo está en la tarifa y no en el kWh;
- quizá la energía visible es síntoma, no sistema.

## 4. Nueva Jerarquía Epistemológica

### 1. Local Truth Claim

Requiere:

- evidencia local fuerte
- binding local suficiente
- dependencia física observada

Lenguaje permitido:

- `observed`
- `asset-level evidence shows`
- `the case demonstrates`

Lenguaje prohibido:

- cualquier cierre sin evidencia local fuerte

### 2. Structural Hypothesis

Permitida si existe:

- arquetipo válido
- trigger plausible
- evidencia mínima definida
- falsación definida

Lenguaje permitido:

- `may`
- `if this asset behaves like`
- `structurally plausible`
- `deserves falsification`

Lenguaje prohibido:

- `this asset has`
- `therefore the retrofit should be`

### 3. Archetypal Prior

Es conocimiento general de industria.

Lenguaje permitido:

- `recurring pattern`
- `archetypal risk`
- `common structural failure mode`

Lenguaje prohibido:

- presentarlo como hecho local

### 4. Weak Signal

Es una señal contextual todavía más débil.

Lenguaje permitido:

- `weak signal`
- `possible clue`
- `ownership signal`

Lenguaje prohibido:

- elevarlo a causalidad o diagnosis

### Regla de uso

El framework debe poder producir outputs en los cuatro niveles.

Lo que no puede hacer es colapsar niveles 2, 3 y 4 dentro del veto aplicado al nivel 1.

## 5. Qué Debe Volver

### Charging demand hypothesis

Debe volver porque en logística y cold chain es un patrón recurrente de costo, no una invención local.

Cómo debe sonar:

`If movement intensity and electric MHE are material, charging overlap may be a stronger cost driver than annual kWh intensity.`

Qué la falsaría:

- ausencia de MHE eléctrico
- ausencia de demanda penalizada
- charging windows sin superposición relevante

### Dock infiltration hypothesis

Debe volver porque en logística/cold chain la interfaz dock-envelope es un driver estructural plausible.

Qué la falsaría:

- baja actividad de dock
- sellado y staging controlados
- nula relación con duty térmico

### Cold-chain split hypothesis

Debe volver porque distinguir warehouse general vs conditioned storage cambia benchmark, CAPEX y variable dominante.

Qué la falsaría:

- ausencia de cold-room duty
- carga térmica irrelevante

### Control boundary leakage

Debe volver porque owner/operator split o process/support split pueden destruir el caso económico aunque el síntoma técnico sea real.

Qué la falsaría:

- frontera control-captura alineada y evidenciada

### Fair comparison logic

Debe volver porque muchas comparaciones son inválidas antes de normalizar intensidad de servicio.

Qué la falsaría:

- peer set normalizado y mismo duty boundary

### Tariff exposure logic

Debe volver porque costo no equivale a kWh. En muchos casos manda demanda, PF o horario.

Qué la falsaría:

- tarifa sin exposición a demanda/PF/TOU material

### Power factor / reactive plausibility

Debe volver en utility-heavy/manufacturing/infrastructure contexts.

Qué la falsaría:

- tarifa indiferente a PF/reactiva
- inventario de cargas sin riesgo inductivo relevante

### Maintenance maturity patterns

Debe volver porque el costo visible puede estar en downtime y no en energía.

Qué la falsaría:

- alta madurez de mantenimiento y bajo impacto de downtime

### Logistics intensity logic

Debe volver porque `per area` puede ser el denominador equivocado.

Qué la falsaría:

- baja intensidad operativa y alta comparabilidad espacial real

### `do not model yet`

Debe volver, pero con semántica correcta:

- no significa `no pensar`
- significa `no cerrar modelado físico/capital`

### `wrong denominator`

Debe volver porque es una de las piezas más valiosas del cerebro.

### `wrong benchmark`

Debe volver porque fair comparison sin normalización es estratégicamente peligrosa.

### `wrong variable`

Debe volver porque el usuario necesita saber si el driver real es tarifa, throughput, dock, schedule, temperature duty, maintenance, boundary, etc.

### `the problem may not be energy`

Debe volver porque eso es exactamente el reframe que diferencia a ZLab.

## 6. Qué Nunca Debe Volver

Las siguientes cosas deben seguir prohibidas:

1. ROI
2. savings claims
3. compliance closure
4. benchmark superiority
5. peer superiority
6. digital twin recommendation
7. retrofit recommendation
8. `this asset has X loss`
9. definitive diagnosis

### Por qué

Porque todas ellas requieren un salto de authority que no se obtiene con:

- archetypal priors
- weak signals
- conditional structural hypotheses

Es correcto bloquearlas.

El error no está ahí.

El error está en bloquear también el pensamiento estructural que **precede** y **gobierna** esas clausuras.

---

## 7. Nuevo Comportamiento Esperado

No debe sonar así:

`Missing GFA, missing operating schedule, asset not modelable.`

Debe sonar así:

`The current framing may be wrong. If this asset behaves as a high-service logistics node, area-based benchmarking could be structurally invalid. The dominant variable may be dock activity, charging windows, refrigeration duty or control boundary rather than generic energy inefficiency. These hypotheses remain conditional and require falsification before any retrofit or modeling effort.`

### Por qué este lenguaje es mejor

1. es más útil porque orienta la siguiente falsación;
2. es más inteligente porque distingue síntoma de sistema;
3. es más estratégico porque cambia benchmark, CAPEX y prioridad;
4. sigue siendo epistemológicamente limpio porque no afirma verdad local;
5. conserva la esencia original del framework.

## 8. Cambios Arquitectónicos Necesarios

### A. Claim Governor

Debe distinguir explícitamente:

1. `local_truth_claim`
2. `structural_hypothesis`
3. `archetypal_prior`
4. `weak_signal`

Hoy el `congruence` claim governor ya sabe permitir estados como `ARCHETYPAL_PRIOR`, `WEAK_SIGNAL` y `CONDITIONAL_HYPOTHESIS`; el problema es que esa distinción no sobrevive hasta el thesis final.

### B. Pattern Activation Engine

Debe permitir activación condicional aunque la identidad del activo esté incompleta.

No debe exigir `operational_asset_candidate` para poder emitir **ningún** patrón.

Debe tener dos salidas:

1. `archetypal_screening_pattern_register`
2. `locally_bounded_pattern_register`

### C. System Abstraction Engine

Debe poder crear `conditional structural abstraction`.

Hoy `system_abstraction.py` devuelve todo como unresolved `INADMISSIBLE_CLAIM` si cae en `target_not_yet_structurally_modelable`.

Eso debe cambiar a:

1. `local_asset_truth_layer` bloqueada
2. `archetypal_structure_layer` todavía activa

### D. Report Composer / Executive Thesis

Debe generar una `conditional intelligence layer` aun cuando el asset-level closure esté bloqueado.

En vez de:

- `inadmissible_thesis -> empty contradiction, empty gold nuggets, empty redesign`

debe haber:

- `non_closable_local_thesis`
- `conditional_structural_intelligence`

### E. Fair Comparison Engine

Debe producir `comparison requirements` incluso si la comparación aún no es admisible.

O sea:

- no peer superiority
- sí comparison invalidity intelligence
- sí normalization requirements

### F. Gold Nugget Engine

Debe producir nuggets acotados, no local truths.

Formato correcto:

- `decision-shock insight`
- `why it matters`
- `minimum evidence`
- `what would falsify it`

No:

- diagnosis
- recommendation
- certainty

## 9. Nuevo Principio Maestro

`Lack of local certainty must block closure, not thinking.`

Versión equivalente:

`The framework must prohibit false certainty without prohibiting structural reasoning.`

### Justificación

Porque el framework existe para generar inteligencia gobernada, no para delegar todo valor al momento en que ya casi no hace falta pensar.

Si sólo permite hablar cuando todo ya está localmente cerrado:

- llega demasiado tarde;
- pierde el reframe;
- pierde la falsación priorizada;
- pierde el warning estructural;
- pierde el gold nugget;
- pierde su ventaja cognitiva.

El problema, por tanto, es de **governed synthesis policy**, no de inexistencia de motores inteligentes.

## Bottom Line

The framework did not become wrong because it became governed.

It became strategically weaker because it now confuses:

- `not enough evidence to close`

with

- `not enough permission to think structurally`

That confusion must be removed.
